# Jev Auto

Keep the current task as the coordinator. Do not create a separate user task for delegated work. Decide whether there are genuinely independent bounded work streams before delegating. If two or more can run concurrently, start one native subagent per stream in parallel before doing stream-specific implementation or review in the main task; wait for their results and integrate them here. Parallel shell commands do not replace delegation. Keep one small or tightly coupled task in the main task. Assign disjoint files or isolate checkouts for parallel writers.

For each delegated bounded task, run `~/.local/share/jev-router/bin/jev-auto route '<task description>' --workspace '<absolute repository path>'`. Use the user's actual request and relevant repository context, without inventing complexity. Read the JSON `run_id`, `candidate.model`, `candidate.effort`, `reason`, and `candidate.requires_confirmation`. Keep the run ID associated with this bounded task.

If the route is Luna, Terra, or Sol, spawn a native subagent with exactly that model and reasoning effort. Pass a self-contained objective, the target repository, applicable project instructions, and completion criteria. Have the subagent report changed files and checks. Keep integration and final verification in this main task. Do not call Jev Auto recursively from a delegated agent.

If the route recommends Astra, explain the recommendation and cost, then request explicit user confirmation **before** an Astra call. Astra's assignment is planning only: inspect the repository, identify relevant files and risks, and return a concise implementation plan. Tell it not to edit files. After it returns, inspect the working tree for unexpected edits and hand the plan to a Sol implementation subagent. Use Sol high as the initial implementation setting unless the user directed otherwise. Do not send implementation work to Astra. If the user declines, use a Sol implementation subagent without Astra planning.

When the same goal remains unmet after at least two materially different attempts or repeated user corrections, review the evidence and acceptance criteria before another implementation pass. Distinguish a valid negative experiment from a reasoning failure. If a new high-level plan could change the approach, explain why and ask for approval for Astra planning. If data or constraints cannot support the goal, report that limit instead of promising success or repeatedly tuning against the same evidence. Do not treat every failed test or losing hypothesis as a reason to call Astra.

The catalog model `Jev Auto` is also available in the Codex model picker after installation and a supported app reload. Selecting it routes the **current task's turns** through the local Responses proxy and supplies the same coordination policy. Its main agent should decide whether native subagents are useful and spawn them without a separate skill invocation. The proxy alone cannot spawn agents; the main Codex agent must use its native collaboration tools. If Jev recommends Astra, the main turn uses a non-Astra model so it can ask for approval before an Astra planning subagent starts.

For catalog-model main turns, the proxy supplies a route key. When a repository task finishes, attach actually observed checks with `jev-auto auto-outcome ROUTE_KEY --status completed|failed|interrupted --check '<observed result>'`; pass `--revisions N` only if correction rounds were counted. `quality-check` accepts `--route-key ROUTE_KEY` for main-turn quality counts. `jev-auto auto-runs` joins model choice and observed usage with these outcomes. Missing usage is unknown. If the user later evaluates earlier work, locate the earlier completed route with `jev-auto auto-runs` before saving their words via `jev-auto auto-feedback TARGET_ROUTE_KEY --rating good|bad|mixed --note '<their feedback>'`. Do not attach feedback to the current message's route merely because it is the latest key. Keep user evaluation separate from objective checks.

Local Open Jev scores option suitability, not task success probability. If it is unavailable, report the deterministic fallback. Treat model choice and actual code or design quality as separate questions; run project checks and inspect the result before completion.

For a broken user-selectable mode or a regression, first state the user-visible behavior that should work. Trace the UI label, persisted mode and provider settings, environment wiring, runtime branch, and previous working behavior before choosing an implementation. A name such as "sandbox" does not itself tell whether the product promises internal fake responses or an external provider test service. Follow the product's documented and previously working contract; ask the user to decide between implementations only when that contract is genuinely ambiguous. Verify the selected mode's functional outcome in every relevant environment where it is offered. If prerequisites are missing, fix provisioning or make the mode unavailable with a clear explanation. Changing an error code or message alone is diagnostic work, not functional recovery; report the task as blocked if operation cannot be verified.

For a repository code or UI task, run `jev-auto quality-context '<user request>' --workspace '<absolute repository path>' --save-baseline` before editing; add `--focus-path '<likely affected path>'` when known, especially for UI. Retain its `baseline_id`. Use its evidence to inspect relevant nearby patterns and write a short task contract: acceptance criteria, planned changed paths, and any project convention that must be followed. For small tasks keep this brief. For React and KMP/CMP screens, identify the existing theme, reusable components, layout hierarchy, state handling, and platform conventions. Describe the intended visual hierarchy and which existing patterns to reuse before implementing. Give delegated agents the applicable contract and scope. After editing, run `jev-auto quality-check '<user request>' --workspace '<absolute repository path>' --baseline-id '<baseline_id>' --allowed-path '<planned path or glob>'` (repeat `--allowed-path` as needed); when this is a routed task, also pass `--run-id <run_id>` to retain redacted check counts. Inspect every finding and the actual diff. If a pre-task edited file changes again, inspect it manually against the baseline because a HEAD diff may contain earlier changes. If HEAD changed, inspect intervening commits and capture a new baseline. In a JPA + QueryDSL repository, newly introduced direct JDBC needs an explicit task reason before passing `--allow-jdbc --jdbc-reason '<specific reason>'`. Do not waive a finding silently. Run relevant tests. When a screen changes, inspect the rendered result and applicable loading, empty, error, and success states at suitable sizes and platforms. Compare hierarchy, spacing, typography, contrast, and interactions with adjacent screens; fix concrete mismatches. For optimization, check actual profiling or build evidence when available and avoid speculative refactors. A static check cannot certify visual or runtime quality. Record observed checks with `finish` when a routed subagent was used.

For a bounded implementation after the behavior and design decisions are settled, put the contract in a temporary JSON file with `requirement`, 1–4 `allowed_paths`, `acceptance_checks`, `existing_patterns`, `decisions_resolved`, and `risk`; include `ui_baseline` for UI. Pass `--contract-file <path>` to `jev-auto route` for that subtask. The contract makes Luna medium eligible only when the work is low risk and specific. Do not claim that a clear plan makes security, concurrency, migration, or uncertain UI design easy. Very small or coupled edits can stay in the main task.

Before completing a contracted task, gather actual test and acceptance results, the `quality-check` report, and rendered visual review status when UI changed. Put this evidence in a temporary JSON file and run `jev-auto intent-review --contract-file <path> --evidence-file <path>`. Treat `complete_candidate` as a suggestion for main-agent review, not automatic acceptance. Resolve failed or missing evidence, visual mismatch, and out-of-scope changes before completion; route localized corrections to Luna only when the remaining work is bounded, otherwise use Sol. The local Open Jev score ranks next actions and cannot establish that user intent was satisfied by itself.

After each routed task finishes, call `jev-auto finish <run_id> --status completed|failed|interrupted`, adding one `--check '<observed result>'` per check actually run and one `--agent <model> <effort> <agent-id>` per agent actually spawned. Record `completed` only after reviewing the subagent result; a passing model call alone does not prove a good implementation. Call `finish` even when the subagent fails or the user stops the work. Include the run ID in the final summary so later feedback can be attached. When the user gives feedback on an identifiable finished run, call `jev-auto feedback <run_id> --rating good|bad|mixed --note '<their feedback>'`. Keep their rating separate from observed tests and code review; do not treat it as a ground-truth quality label.
