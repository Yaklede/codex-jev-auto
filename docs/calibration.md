# 라우팅 보정과 공동 검증

## 현재 상태

Open Jev의 기본 Gemma 점수만으로 20개 조합을 고르면 간단한 수정부터 큰 설계 작업까지 거의 모두 Luna/high로 향했다. 2026-09-25에 정규화를 `pmi`로 바꾸고, 작업 범위와 위험 신호에 따라 허용 가능한 모델·추론 강도 범위를 적용했다. 고정 규칙에 걸리지 않은 요청은 Open Jev가 작은 국소 수정인지 먼저 분류한다. 일반 요청에서는 사용 가능한 20개 조합을 모두 점수화하고, 정책 범위 안의 최고 점수를 고른다. 두 메뉴 모두 후보 순서를 뒤집어도 선택이 같은지 확인한다. 사용자가 Astra를 명시적으로 요청하면 점수화보다 그 지시를 우선하며, 실행 전 승인은 그대로 필요하다.

매우 어려운 작업에서는 Astra를 **계획 전용**으로 추천할 수 있다. 사용자가 해당 실행을 승인한 경우에만 Astra가 읽기 전용 저장소에서 계획을 만들고, Sol/high가 코드를 구현한다. 계획 단계가 실패하거나 저장소를 변경하면 구현을 시작하지 않는다. 현재까지 실제 Astra 계획 호출은 하지 않았고, 승인 및 안전 경로는 모의 모델을 사용한 테스트로 검증했다.

## 재현 가능한 평가

사례와 임시 허용 범위는 [`evals/router_cases.json`](../evals/router_cases.json)에 있다. `development`는 정책을 조정하는 데 사용했다. 초기 `holdout`의 일부도 결과를 보고 규칙을 고쳤으므로 더 이상 독립 검증 자료가 아니다. 이후 새로 만든 [`router_holdout_v2.json`](../evals/router_holdout_v2.json)은 현재 정책을 바꾸지 않고 한 번만 실행했다. 결과는 [`baseline.json`](../evals/baseline.json), [`calibrated-v5.json`](../evals/calibrated-v5.json), [`holdout-v2-result.json`](../evals/holdout-v2-result.json)에 있다.

| 단계 | 개발용 사례 | 별도 검증 사례 | 의미 |
| --- | ---: | ---: | --- |
| 기본 Gemma 점수 | 2/9 | 0/4 | 모델 이름과 표현에 치우친 선택이 많음 |
| PMI + 난도 범위 | 9/9 | 2/4 | 쉬운 일과 위험한 일을 구분하지만, 일부 보통 난도 작업의 추론 강도가 낮음 |
| Astra 계획 경로와 국소 수정 분류 | 12/12 | 기존 6/6 | 작은 일은 Luna/medium, 매우 어려운 일은 승인 대기형 Astra 계획 |
| 현재 정책의 새 보류 사례 | — | 7/8 | 한 설정 상수 수정에 Terra/high가 선택되는 과대 배정 발견 |

이 수치는 **사람이 임시로 정한 모델 범위와의 일치율**이다. 코드 품질, 성공률, 실제 비용 절감률이 아니다. 개발용 사례에 맞춘 정책이므로 12/12를 일반화하면 안 된다. 새 보류 사례의 과대 배정도 실제 사용자 작업에서 얼마나 비용을 낭비하는지 확인해야 한다.

평가 재실행:

```sh
cd plugins/jev-router
uv run python ../../scripts/evaluate_router.py --output ../../evals/latest.json
uv run python ../../scripts/evaluate_router.py --cases ../../evals/router_holdout_v2.json --output ../../evals/latest-holdout.json
```

## 다음 검증 절차

1. 사용자 저장소의 실제 작업에서 쉬운 수정, 보통 규모 기능, 어려운 백엔드 오류, 프론트엔드 화면 개편을 각각 모은다. 각 작업의 시작 커밋, 기존 변경, 완료 조건을 기록한다.
2. 라우터의 선택을 먼저 기록하고, 실제 구현에 앞서 사용자가 과소·과대 선택이라고 느낀 사례에 표시한다. 이 피드백으로 임시 허용 범위를 고친다.
3. 대표 작업만 선택 모델과 Sol 기준 실행을 같은 시작 상태에서 비교한다. 20개 조합을 모두 실행하지 않는다. 테스트 결과, 코드 구조, UI 화면, 소요 시간, 모델 사용량을 함께 본다.
4. 매우 어려운 작업 한두 건은 사용자가 Astra **계획 실행을 직접 승인한 뒤**, `Sol 단독`과 `Astra 계획 + Sol 구현`을 비교한다. 계획의 정확성, 구현 품질, 총 사용량을 모두 확인한다.
5. 정책을 고칠 때마다 새로운 보류 사례를 추가한다. 기존 보류 사례를 보고 고친 뒤에는 그 사례를 더 이상 독립 검증으로 계산하지 않는다.

현재의 4개 보류 사례만으로 품질 보정을 완료했다고 볼 수 없다. 실제 작업의 결과와 사용자 선호가 들어와야 모델별 경계와 Astra 계획의 이득을 확정할 수 있다.
