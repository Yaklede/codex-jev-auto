# Jev 라우팅 플러그인 개발 기획

상태 (2026-09-25): 1차 라우팅 시제품을 로컬 플러그인으로 설치했고, Gemma 3 점수화와 MCP를 통한 백엔드·프론트엔드 실제 작업을 검증했다. Astra 승인 전 차단도 MCP에서 확인했다. 이후 난도별 보정과 **Astra 읽기 전용 계획 → Sol 구현** 경로를 추가했다. 보정 결과와 한계는 [라우팅 평가](calibration.md)에, 기존 통합 시험은 [1차 검증 기록](phase1-verification.md)에 있다. Codex Desktop의 실제 Astra 확인 UI와 실제 Astra 계획 호출은 아직 검증하지 않았다.

현재 저장소 프로필 수집은 파일 수·주요 언어·기존 변경 여부와 요청 문구의 간단한 유형/범위 판별까지 구현됐다. 아래의 관련 모듈·위험도·비용 상한 분석은 기획 항목이며 아직 구현되지 않았다.

## 1. 목표

사용자가 Codex에서 플러그인에 개발 작업을 맡기면, 플러그인이 작업의 특성과 저장소 문맥을 조사하고 **모델 4개 × 추론 강도 5개 = 20개 설정**을 비교한다. 로컬 Open Jev가 설정을 선택하는 데 참여한다. Astra가 선택되면 승인 후 계획만 작성하고 Sol이 구현한다.

**1차 구현 범위는 모델·추론 강도 선택, 선택한 설정으로 작업 실행, Astra 계획 전 사용자 확인, 실행 결과 기록까지다.** Astra 계획은 읽기 전용이며 Sol이 구현한다. Codex가 해당 프로젝트의 기존 테스트를 실행할 수는 있지만, 하네스 전용 코드 품질 심사나 UI 디자인 개선 루프는 1차 범위에 넣지 않는다. 이 품질 기능은 같은 플러그인 안에 후속 단계로 추가한다.

Open Jev는 4개 후보 모델에 포함되지 않는다. 로컬의 선택기이며 코드를 생성하지 않는다. GPT-6 Astra로 계획을 세우기 전에는 매번 사용자 확인을 받는다. Astra는 이 플러그인에서 코드를 수정하지 않는다.

## 2. 실행 설정 매트릭스

추론 강도는 `low / medium / high / xhigh / max`로 고정한다. 한국어 표시명은 `낮음 / 중간 / 높음 / 매우 높음 / 최대`다.

| 모델 | 낮음 | 중간 | 높음 | 매우 높음 | 최대 |
| --- | --- | --- | --- | --- | --- |
| GPT-6 Luna | L1 | L2 | L3 | L4 | L5 |
| GPT-5.6 Terra | T1 | T2 | T3 | T4 | T5 |
| GPT-6 Sol | S1 | S2 | S3 | S4 | S5 |
| GPT-6 Astra | A1 | A2 | A3 | A4 | A5 |

사용자가 제안한 GPT-6 Terra는 2026-09-25 공식 모델 목록에서 확인되지 않아, 합의한 대로 GPT-5.6 Terra를 사용한다. 실행 시 Codex `model/list`에서 계정에 표시되는 모델과 지원 추론 강도를 확인한다. 따라서 20칸은 목표 매트릭스이고, 실제 사용 가능 조합은 검증 결과로 확정한다.

## 3. 1차 구현: 플러그인 호출부터 완료까지

```text
사용자: 플러그인에 작업 요청
  → 라우팅에 필요한 저장소 조사: 언어, 프레임워크, 관련 모듈, 변경 범위
  → 작업 프로필 작성: backend/frontend/mixed, 범위, 모호성, 위험도
  → 현재 계정에서 사용 가능한 20개 조합 확인
  → 금지/예산/지원 불가 조합 제외
  → Open Jev가 남은 조합을 한 번에 비교
  → 일반 작업: 선택된 모델·추론 강도로 Codex 실행
  → Astra 선택: 사용자 승인 → Astra 읽기 전용 계획 → Sol 구현
  → Codex의 일반 작업 흐름에 따라 구현과 필요한 테스트 수행
  → 변경 내용, 실행 결과, 사용 설정과 시간/사용량 보고
```

선택 결과가 Astra이면 `대기` 상태로 전환하고 계획 모델·추론 강도·Sol 구현 모델·작업 범위를 보여준다. **사용자가 계획 실행을 확인한 뒤에만** Astra를 읽기 전용으로 시작한다. 확인이 없으면 구현도 시작하지 않는다. 재시도하거나 별도 작업을 시작할 때도 다시 확인한다.

라우팅은 기본적으로 **작업 단위**로 고정한다. 1차에는 자동 모델 상향을 넣지 않는다. 실패 상태와 선택 결과를 기록해 후속 단계에서 상향 정책을 평가한다.

## 4. 초기 계획에서 Jev가 판단하는 것

Jev 입력은 사용자 요청만이 아니다. 플러그인이 먼저 다음 항목을 수집한다.

- 작업 유형: 조사, 단일 파일 수정, 멀티파일 구현, 아키텍처 변경, UI 신설/개편
- 저장소 규모와 관련 파일/모듈 수, 테스트 및 기존 컴포넌트 위치
- 요구사항의 모호성, 오류 시 영향, 외부 계약·데이터 변경 여부
- UI 작업인지와 시각적 설계 범위
- 사용자의 비용/시간 상한과 Astra 허용 여부

Open Jev에는 `task_profile + 근거 + 20개 설정 설명`을 넘긴다. 단순히 모델 ID 20개를 나열해 언어모델의 이름 선호도를 재는 방식은 피한다. 후보 설명에는 모델 역량과 추론 강도의 역할을 같은 형식으로 적는다. 옵션 순서를 바꿔 재평가하고, 결과가 흔들리면 기본 정책으로 돌아간다.

초기 기본 정책은 `Sol medium`이다. Jev가 추천한 설정이 더 싸거나 더 강하더라도 바로 신뢰하지 않고, 작업 분류 규칙과 실제 평가 데이터로 검증한다. Open Jev의 softmax 값은 **상대 순위**이지 품질 성공 확률이나 승인 점수가 아니다. 각 작업에서 20개를 모두 실제 실행하는 것은 비용이 크므로, 평가는 대표 사례에서 선택된 설정과 비교 설정을 표본 실행한다.

## 5. 후속 확장: 결과물 품질 개선

### 2차 — 백엔드: 작업 난도에 맞는 코드

쉬운 작업에는 작은 변경과 기존 패턴 재사용을 우선한다. 필요 없는 인터페이스·계층·서비스·범용 추상화를 추가했는지 검사한다. 어려운 작업에는 의존 방향, 경계, 실패 처리, 테스트 가능성 등 필요한 구조를 충분히 설계한다. **작업의 난도와 코드의 복잡도를 비례시키는 것**이 목표다. 컴파일·테스트·정적 검사·프로젝트 규칙은 도구로 확인하고, Jev는 선택 가능한 구현 접근을 비교한다.

### 3차 — 프론트엔드: 정돈된 코드와 더 나은 화면

코드는 기존 컴포넌트·디자인 토큰·상태 관리 방식과 일치하게 정리한다. 화면은 주 사용자 행동, 정보 위계, 간격, 밀도, 반응형 상태를 고려해 설계한다. 웹은 DOM/접근성 트리/화면 크기별 스크린샷을, React Native는 대상 플랫폼의 화면 캡처와 접근성 정보를 수집한다. 오버플로와 접근성 오류는 도구로 확인하고, 실제 시각적 완성도는 스크린샷과 사용자 피드백으로 평가한다. Jev는 텍스트로 구조화된 후보와 증거를 비교하며, 이미지를 직접 심사하지 않는다.

2·3차부터 품질 검토 결과를 짧은 수정 지침으로 작업 모델에 다시 전달한다. 재시도 횟수와 모델 상향 횟수는 제한해 반복 루프를 막는다. Astra 상향에는 매번 사용자 확인을 받는다.

## 6. 플러그인 구조

```text
Codex에서 플러그인 호출
  └─ Skill: 전체 작업 순서와 보고 형식
      └─ 로컬 MCP 도구: route_and_run / status / run_astra / feedback
          └─ Orchestrator: 작업 프로필, 20칸 정책, 실행 상태
              ├─ Open Jev 로컬 서버: 후보 점수화
              ├─ Codex Python SDK → App Server: 선택한 model + effort로 작업 실행
              ├─ 후속 확장: 백엔드/프론트엔드 품질 어댑터
              └─ 실행·평가 기록
```

Skill만으로는 이미 시작된 Codex 대화의 모델을 선택 전에 바꿀 수 없다. 플러그인을 호출한 대화는 진행을 안내하는 조정자이고, 로컬 MCP 도구가 **선택된 설정의 별도 Codex 작업 세션**을 실행한다. 선택된 모델은 이 작업 세션에 적용된다. 결과와 진행 상황은 원래 대화에 반환한다. 별도 세션이 Codex Desktop의 작업 목록에 자동으로 표시되는지는 첫 시제품에서 검증한다.

실행기는 우선 Codex Python SDK를 사용한다. 이 SDK는 App Server를 통해 모델 목록을 조회하고, 스레드 또는 턴에 `model`과 `effort`를 설정하고, 실행 이벤트를 받을 수 있다. 필요한 기능이 SDK에 없을 때만 App Server JSON-RPC를 직접 사용한다. 플러그인의 MCP 작업은 오래 걸릴 수 있으므로 `route_and_run`은 작업 ID를 즉시 반환하고 `status`로 진행 상황을 읽는다. 사용자 입장에서는 플러그인을 한 번 호출하지만 내부에서는 여러 도구 호출과 상태 조회가 일어난다.

Astra는 별도 확인 도구 `run_astra`로만 계획을 시작할 수 있게 하고, 일반 `route_and_run`은 Astra 추천 시 실행하지 않고 대기한다. MCP의 사용자 입력 요청으로 계획 모델·강도·Sol 구현 모델·범위를 보여주고, 사용자의 명시적 수락 결과를 받은 경우에만 읽기 전용 Astra 계획을 시작한다. 계획이 실패하거나 저장소를 변경하면 Sol 구현을 시작하지 않는다. 이 입력 요청이 Codex Desktop에서 지원되는지는 아직 검증하지 않았다. 다른 모델 경로는 사용자가 플러그인을 호출한 권한 범위 안에서 자동 진행한다.

작업 실행 전에는 현재 Git 상태와 변경 파일을 기록하고 저장소별 동시 실행을 제한한다. 첫 버전은 현재 체크아웃에서 작업하되, 사용자의 기존 변경을 지우거나 초기화하지 않는다. 결과에는 시작 시점과 비교한 diff를 포함한다. 별도 worktree 실행은 기존 변경 반영·결과 적용 흐름을 검증한 뒤 추가한다.

### 구현 언어

1차는 **Python**으로 작성한다. 로컬 MCP 서버는 공식 Python MCP SDK를 사용하고, Open Jev는 별도 프로세스의 `/score` API로 호출하며, 작업 실행은 Codex Python SDK로 연결한다. 라우팅 정책은 외부 의존성이 적은 순수 Python 모듈로 분리해 테스트한다. 이 단계의 주된 지연은 모델 추론과 Codex 작업 실행에서 발생하므로, 측정 없이 Rust로 실행기를 먼저 작성하지 않는다. 이후 저장소 분석이나 대량 후보 평가에서 실제 병목이 확인되면 해당 부분만 Rust로 분리할 수 있다.

## 7. 개발 단계

1. **1차 — 라우팅 플러그인:** 4개 모델의 가용성과 5개 강도 지원 여부 확인, 작업 프로필, 20개 후보 비교, Astra 계획 승인과 Sol 구현, 결과·사용량 기록. 백엔드 작업 1건과 프론트엔드 작업 1건으로 호출부터 결과 반환까지 검증한다.
2. **2차 — 백엔드 품질:** 쉬운 작업의 불필요한 복잡도와 어려운 작업의 구조적 누락을 탐지하고, 프로젝트의 기존 코드 패턴을 반영한 수정 루프를 추가한다.
3. **3차 — 프론트엔드 품질:** 공통 컴포넌트·토큰·상태 처리 준수와 실제 화면의 정보 위계·사용 흐름·시각적 완성도를 평가하는 수정 루프를 추가한다.
4. **4차 — 통합 평가와 정책 보정:** 기본 Codex 결과와 플러그인 결과를 가리고 비교해 라우팅, 코드 품질, UI 품질의 효과를 각각 측정한다. 검증된 범위에서만 자동 상향·자동 품질 게이트를 도입한다.

## 8. 성공 판정

**1차 완료 조건:** 플러그인 호출 한 번으로 유효한 모델·강도를 선택해 작업을 실행하고, Astra 계획은 명시적 확인 없이는 실행되지 않으며 코드를 수정하지 않는다. 계획이 선택되면 Sol이 구현하고, 선택·계획·실행·결과가 재현 가능한 기록으로 남는다.

**최종 성공 조건:** 같은 시작 커밋과 요구사항으로 기본 Codex 흐름과 플러그인 흐름을 비교했을 때, 사람이 더 좋은 코드와 화면을 선택하고 결함·재작업이 늘지 않는다. 백엔드와 프론트엔드는 따로 집계한다. Jev의 라우팅 정확도와 최종 결과물 품질도 별도로 측정한다.
