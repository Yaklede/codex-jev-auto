# Jev Auto 실행 구조

## 메인 작업에서 호출

```text
사용자의 기존 Codex 작업 (모델은 사용자가 선택)
  → $jev-auto 스킬
  → 로컬 CLI가 저장소와 요청을 Open Jev로 점수화
  → 모델·추론 강도 결정
  → Codex 기본 서브에이전트에 선택값 전달
  → 메인 작업이 결과와 테스트를 확인
```

이 경로는 기존 작업 ID와 대화 문맥을 보존한다. 작업 요청마다 별도 사용자 작업을 만들지 않는다. 서브에이전트는 Codex가 제공하는 기본 협업 도구를 사용한다. 스킬 로딩은 작업 생성 시점에 따라 달라지므로, 설치 전에 시작한 긴 작업은 새 스킬을 자동으로 발견하지 못할 수 있다. 그 경우 해당 작업에서 CLI를 직접 호출해 동일한 결정을 얻을 수 있으며, 새 작업으로 이전해야 한다고 가정하지 않는다.

## 모델 선택기의 Jev Auto

```text
Codex 모델 카탈로그의 `jev-auto`
  → 현재 작업의 Responses HTTP/WebSocket 요청
  → 127.0.0.1:18084 프록시
  → 로컬 Open Jev가 턴의 사용자 요청을 점수화
  → 실제 모델·추론 강도로 바꿔 기존 인증과 함께 상위 API에 전달
```

이 경로에서는 **현재 작업 자체의 턴**이 선택된 모델을 사용한다. 서브에이전트 생성은 별도의 스킬 동작이다. 따라서 메인 작업을 특정 모델의 조정자로 유지하려면 모델 선택기에서 그 구체 모델을 고른 채 스킬을 호출한다.

설치기는 현재 Codex 모델 목록을 보존한 카탈로그에 `Jev Auto`를 추가한다. 설정에는 `model_catalog_json`과 `openai_base_url`을 추가하며, 기존 설정의 백업을 저장한다. `jev-auto restore`로 이 두 설정과 LaunchAgent를 복원한다. 다른 모델 요청은 동일한 프록시를 통과하지만 모델 이름을 바꾸지 않는다. 프록시가 죽으면 Codex의 API 요청도 실패하므로 서비스 상태를 먼저 확인한다.

## Astra 정책

매우 어려운 작업에서 Astra가 추천되면 실행 전 사용자 확인이 필요하다. 스킬은 승인 후 Astra 서브에이전트를 계획 작성에만 사용하고 Sol에 구현을 넘긴다. 직접 모델 선택기에서 Jev Auto를 쓴 턴은 Astra 추천 시 409/웹소켓 정책 오류로 중단한다. 현재 프록시는 승인 없이 Astra 요청을 통과시키는 우회 기능을 제공하지 않는다. 기본 서브에이전트 도구에는 파일 쓰기를 기술적으로 금지하는 옵션이 없어, Astra 계획 단계의 읽기 전용성은 지시와 메인 작업의 변경 상태 점검으로 확인해야 한다.

## 검증과 아직 남은 범위

라우팅은 요청과 간단한 저장소 프로필을 평가한다. 점수는 품질 성공률이 아니다. 모델 전환, HTTP/WebSocket 전달, 카탈로그 파싱, Astra 차단을 검증한다. Desktop 모델 선택기의 표시 여부와 긴 작업의 스킬 재로딩은 Desktop 빌드에서 별도로 확인한다.

백엔드는 쉬운 작업에 단순한 코드를 쓰고 어려운 작업에 필요한 구조를 적용해야 한다. 프론트엔드는 기존 컴포넌트와 토큰을 지키면서 더 좋은 화면을 검토해야 한다. 이 품질 평가·피드백 루프는 라우터 구현 다음 단계이며 현재 라우팅만으로 보장되지 않는다.
