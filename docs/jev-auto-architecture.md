# Jev Auto 실행 구조

## 메인 작업에서 호출

```text
사용자의 기존 Codex 작업 (모델은 사용자가 선택)
  → $jev-auto 스킬
  → 독립적인 하위 작업이 있으면 작업마다 로컬 CLI로 점수화
  → 선택한 모델·추론 강도로 Codex 기본 서브에이전트 병렬 실행
  → 메인 작업이 결과와 테스트를 확인하고 실행 ID에 기록
```

하위 작업이 하나이고 작거나 긴밀히 결합돼 있으면 메인이 직접 처리하며 서브에이전트 실행 ID는 만들지 않는다. 이 경로는 기존 작업 ID와 대화 문맥을 보존한다. 작업 요청마다 별도 사용자 작업을 만들지 않는다. 서브에이전트는 Codex가 제공하는 기본 협업 도구를 사용한다. 스킬 로딩은 작업 생성 시점에 따라 달라지므로, 설치 전에 시작한 긴 작업은 새 스킬을 자동으로 발견하지 못할 수 있다. 그 경우 해당 작업에서 CLI를 직접 호출해 동일한 결정을 얻을 수 있으며, 새 작업으로 이전해야 한다고 가정하지 않는다.

## 모델 선택기의 Jev Auto

```text
Codex 모델 카탈로그의 `jev-auto`
  → 현재 작업의 Responses HTTP/WebSocket 요청
  → 127.0.0.1:18084 프록시
  → 로컬 Open Jev가 턴의 사용자 요청을 점수화
  → 실제 모델·추론 강도로 바꿔 기존 인증과 함께 상위 API에 전달
  → 메인 에이전트에 조정·위임 정책 전달
  → 독립적인 하위 작업이면 작업별 재라우팅 후 기본 서브에이전트 병렬 실행
  → 메인이 결과 통합·검증
```

이 경로에서는 **현재 작업 자체의 턴**이 선택된 모델을 사용한다. 프록시는 조정 정책을 턴 지시에 추가한다. 메인 에이전트는 독립적인 작업을 판단해 필요한 경우 기본 서브에이전트를 만들도록 지시받는다. 프록시 자체에는 에이전트 생성 권한이 없고, 지시만으로 실제 생성을 보장할 수 없다. 작업별 라우팅은 로컬 CLI로 수행하며, 중복 파일 수정 위험이 있으면 소유권을 나누거나 격리된 체크아웃을 사용한다. 작거나 서로 의존하는 작업은 메인이 직접 맡는다. 짧은 "진행해" 같은 후속 요청은 안정적인 세션 식별자가 있을 때 이전 사용자 작업을 최대 1,600자만 덧붙여 점수화한다. 도구 응답만 있는 이어쓰기에서는 그 세션의 선택을 유지한다. 식별자가 없으면 동일 문장이라는 이유로 다른 작업의 결정을 재사용하지 않는다. 프록시는 신뢰할 수 있는 저장소 경로를 받지 못하는 경우 저장소 프로필을 추측하지 않는다.

설치기는 현재 Codex 모델 목록을 보존한 카탈로그에 `Jev Auto`를 추가한다. 설정에는 `model_catalog_json`과 `openai_base_url`을 추가하며, 기존 설정의 백업을 저장한다. `jev-auto restore`로 이 두 설정과 LaunchAgent를 복원한다. 다른 모델 요청은 동일한 프록시를 통과하지만 모델 이름을 바꾸지 않는다. 프록시가 죽으면 Codex의 API 요청도 실패하므로 서비스 상태를 먼저 확인한다.

## Astra 정책

매우 어려운 작업에서 Astra가 추천되면 실행 전 사용자 확인이 필요하다. 메인 턴은 비 Astra 모델로 계속 진행하며 승인 여부를 묻도록 지시받는다. 승인 후 Astra 서브에이전트를 계획 작성에만 사용하고 Sol에 구현을 넘기도록 지시한다. 프록시는 승인 없이 Astra를 **메인 모델로** 상위 API에 보내지 않는다. 서브에이전트의 승인 확인과 계획 전용 범위는 메인 모델의 지시 준수와 변경 상태 점검에 의존하므로 기술적 강제는 아니다.

반복된 수정 실패가 요청에 명시되거나 전달된 대화에 미해결 보고와 사용자 정정이 함께 있으면 `replan_review`로 분류한다. 이 단계는 Astra를 직접 추천하지 않고 Sol high 또는 xhigh로 이전 시도와 목표를 검토한다. 메인은 서로 다른 접근이 실제로 실패했는지, 데이터와 합격 기준이 타당한지 확인한 다음 새로운 계획이 도움 될 때만 Astra 계획 에이전트의 승인을 요청한다. 부정적인 실험 결과 하나만으로 모델을 올리지 않는다. 프록시가 이전 턴을 전달받지 못하면 이력 신호는 불완전하며, 메인의 대화 검토가 보완한다.

## 검증과 아직 남은 범위

라우팅은 요청과 간단한 저장소 프로필을 평가한다. 점수는 품질 성공률이 아니다. 모델 전환, HTTP/WebSocket 전달, 카탈로그 파싱, Astra의 비승인 직접 호출 차단을 검증한다. `jev-auto doctor`는 설정·서비스·CLI 카탈로그를 검사하지만 Desktop에서 메인이 실제로 자동 위임하는지는 별도로 확인해야 한다.

스킬 경로의 `route`는 실행 ID와 선택값을 반환하고, 같은 ID에 `finish`로 실제 검증 상태와 작업 전후 Git 상태를 저장한다. 사용자가 평가하면 `feedback`으로 해당 ID에 덧붙인다. 스킬은 작업 종료 전에 이 명령을 호출하므로 사용자가 직접 기록할 필요는 없다. 중단된 턴처럼 스킬이 종료 명령을 실행하지 못한 경우에는 미완료 기록이 남는다.

모델 선택기의 메인 턴에는 route key가 부여된다. HTTP SSE와 WebSocket 종료 이벤트에서 사용량과 완료·실패·취소 상태를 요청 내용 없이 기록하고, 응답에 usage가 없으면 미상으로 둔다. 완료 이벤트가 없는 정상 HTTP 응답도 `unverified`로 남긴다. `jev-auto auto-runs`는 모델 선택·확인된 사용량·작업 결과를 묶어 보여 준다. 메인이 `auto-outcome ROUTE_KEY --status ... --check ...`를 실행하면 검증 내용을 연결한다. 사용자가 나중에 평가하면 `auto-runs`로 이전 대상 key를 먼저 찾아 `auto-feedback`으로 저장한다. 현재 피드백 메시지의 새 key를 이전 작업에 붙이지 않는다. `--revisions`는 실제로 확인한 수정 라운드 수이며, 자동으로 추정하지 않는다. route key가 없는 이전 기록과 클라이언트가 사용량을 제공하지 않은 응답의 비용은 복원할 수 없다. 이 기록을 학습 정답으로 직접 취급하지 않는다.

## 저장소 관례와 변경 범위 검사

선택 가능한 모드가 실패하거나 이전에 되던 기능이 회귀한 경우, 메인은 오류 코드보다 먼저 사용자에게 약속한 동작을 완료 조건으로 고정한다. UI 표시·저장된 설정·환경별 연결·실행 분기와 과거 정상 경로를 대조해 해당 모드의 실제 의미를 확인한다. 예를 들어 `sandbox`라는 이름만으로 내부 모의 응답과 외부 업체 테스트망 중 하나를 임의로 선택하지 않는다. 모드가 제공되는 각 환경에서 약속한 기능이 동작하는지 검증하며, 필수 설정이 없다면 설정을 복구하거나 유효하지 않은 모드 선택을 막는다. 오류 문구 변경만으로 기능 복구를 완료 처리하지 않는다. 제품 계약이 명확하면 구현 방식을 사용자에게 선택시키지 않고 그 계약을 따른다.

코드·UI 작업을 시작할 때 메인은 `jev-auto quality-context '<요청>' --workspace '<저장소>'`를 실행한다. 대상 파일을 짐작할 수 있으면 `--focus-path`로 지정해 주변 프론트엔드 컴포넌트와 토큰 사용 근거를 수집한다. 메인은 사용자 요구사항을 완료 조건으로 정리하고, 수정할 경로와 적용할 기존 관례를 구현 에이전트에 전달한다. 작은 작업에는 짧은 계획을 사용한다.

구현 후 `jev-auto quality-check '<요청>' --workspace '<저장소>' --allowed-path '<예정 경로>'`를 실행한다. 라우팅된 하위 작업의 실행 ID가 있으면 `--run-id`, 모델 선택기 메인 경로면 `--route-key`를 추가해 검사 건수와 종류를 해당 실행 기록에 연결한다. 요청 텍스트나 변경 코드 줄은 실행 기록에 복사하지 않는다. 검사기는 `HEAD` 대비 변경 파일과 추가 코드 줄을 확인한다. 계획한 경로 밖의 변경은 검토 대상으로 표시한다. 빌드 파일과 소스에서 JPA와 QueryDSL 사용 근거가 함께 확인되면 새 직접 JDBC 사용을 경고한다. 예외가 필요한 작업은 `--allow-jdbc --jdbc-reason '<구체적 사유>'`를 명시한다. 단순 CRUD에는 JPA Repository, 동적 조회에는 기존 QueryDSL 패턴을 우선 고려한다.

React와 KMP/CMP Compose 화면에서는 변경 후보 주변의 컴포넌트·테마·상태 처리 관례를 제한적으로 읽는다. 기존 디자인 시스템과 화면 위계를 먼저 확인하고, 새 화면은 그 근거를 바탕으로 설계한다. 변경 후에는 정적 근거가 있는 디자인 토큰·상태·성능 위험을 검토 대상으로 표시하고, 기본·로딩·빈 상태·오류·성공 상태와 대상 플랫폼의 화면 크기·접근성을 실제 렌더링에서 확인하도록 안내한다. 최적화는 실제 프로파일링이나 빌드 증거가 있을 때만 성공으로 보고한다. 정적 검사는 실제 시각 품질, 실행 성능, 사용자 요구사항 충족을 판정하지 않는다. 메인이 diff와 테스트 및 화면 결과를 검토한다.

이 경로는 **메인 에이전트에 검사 명령을 호출하도록 지시하는 방식**이다. 프록시가 코드 수정이나 완료 응답을 기술적으로 차단하지는 않는다. 이미 작업 트리에 변경이 있다면 `quality-check`의 `HEAD` 기준 diff에 이전 변경도 포함된다. 메인은 작업 전 Git 상태와 비교해 이번 작업의 변경을 구분한다. 따라서 이 결과만으로 자동 품질 합격이나 자율 학습을 주장하지 않는다.
