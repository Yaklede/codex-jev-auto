# Jev Auto 실행 구조

## 메인 작업에서 호출

```text
사용자의 기존 Codex 작업 (모델은 사용자가 선택)
  → $jev-auto 스킬
  → 독립적인 하위 작업이 있으면 작업마다 로컬 CLI로 점수화
  → 선택한 모델·추론 강도로 Codex 기본 서브에이전트 병렬 실행
  → 메인 작업이 결과와 테스트를 확인하고 실행 ID에 기록
```

하위 작업이 하나이고 작거나 긴밀히 결합돼 있으면 메인이 직접 처리하며 서브에이전트 실행 ID는 만들지 않는다. 이 경로는 기존 작업 ID와 대화 문맥을 보존한다. 작업 요청마다 별도 사용자 작업을 만들지 않는다. 서브에이전트는 Codex가 제공하는 기본 협업 도구를 사용한다. 스킬 로딩은 작업 생성 시점에 따라 달라지므로, 설치 전에 시작한 긴 작업은 새 스킬을 자동으로 발견하지 못할 수 있다. 그 경우 해당 작업에서 CLI를 직접 호출해 동일한 결정을 얻을 수 있으며, 새 작업으로 이전해야 한다고 가정하지 않는다.

## 모델 선택기의 Jev Auto

```text
Codex 모델 카탈로그의 `jev-auto`
  → 현재 작업의 Responses HTTP/WebSocket 요청
  → 127.0.0.1:18084 프록시
  → 로컬 Open Jev가 턴의 사용자 요청을 점수화
  → 실제 모델·추론 강도로 바꿔 기존 인증과 함께 상위 API에 전달
  → 메인 에이전트에 조정·위임 정책 전달
  → 독립적인 하위 작업이면 작업별 재라우팅 후 기본 서브에이전트 병렬 실행
  → 메인이 결과 통합·검증
```

이 경로에서는 **현재 작업 자체의 턴**이 선택된 모델을 사용한다. 프록시는 조정 정책을 턴 지시에 추가한다. 메인 에이전트는 독립적인 작업을 판단해 필요한 경우 기본 서브에이전트를 만들도록 지시받는다. 프록시 자체에는 에이전트 생성 권한이 없고, 지시만으로 실제 생성을 보장할 수 없다. 작업별 라우팅은 로컬 CLI로 수행하며, 중복 파일 수정 위험이 있으면 소유권을 나누거나 격리된 체크아웃을 사용한다. 작거나 서로 의존하는 작업은 메인이 직접 맡는다.

설치기는 현재 Codex 모델 목록을 보존한 카탈로그에 `Jev Auto`를 추가한다. 설정에는 `model_catalog_json`과 `openai_base_url`을 추가하며, 기존 설정의 백업을 저장한다. `jev-auto restore`로 이 두 설정과 LaunchAgent를 복원한다. 다른 모델 요청은 동일한 프록시를 통과하지만 모델 이름을 바꾸지 않는다. 프록시가 죽으면 Codex의 API 요청도 실패하므로 서비스 상태를 먼저 확인한다.

## Astra 정책

매우 어려운 작업에서 Astra가 추천되면 실행 전 사용자 확인이 필요하다. 메인 턴은 비 Astra 모델로 계속 진행하며 승인 여부를 묻도록 지시받는다. 승인 후 Astra 서브에이전트를 계획 작성에만 사용하고 Sol에 구현을 넘기도록 지시한다. 프록시는 승인 없이 Astra를 **메인 모델로** 상위 API에 보내지 않는다. 서브에이전트의 승인 확인과 계획 전용 범위는 메인 모델의 지시 준수와 변경 상태 점검에 의존하므로 기술적 강제는 아니다.

## 검증과 아직 남은 범위

라우팅은 요청과 간단한 저장소 프로필을 평가한다. 점수는 품질 성공률이 아니다. 모델 전환, HTTP/WebSocket 전달, 카탈로그 파싱, Astra의 비승인 직접 호출 차단을 검증한다. `jev-auto doctor`는 설정·서비스·CLI 카탈로그를 검사하지만 Desktop에서 메인이 실제로 자동 위임하는지는 별도로 확인해야 한다.

스킬 경로의 `route`는 실행 ID와 선택값을 반환하고, 같은 ID에 `finish`로 실제 검증 상태와 작업 전후 Git 상태를 저장한다. 사용자가 평가하면 `feedback`으로 해당 ID에 덧붙인다. 스킬은 작업 종료 전에 이 명령을 호출하므로 사용자가 직접 기록할 필요는 없다. 중단된 턴처럼 스킬이 종료 명령을 실행하지 못한 경우에는 미완료 기록이 남는다. 모델 선택기 프록시 경로에는 아직 작업 결과가 연결되지 않는다. 이 기록으로 선택 품질을 비교하기 전에 검증 결과와 사용자 평가의 차이를 유지한다.

백엔드는 쉬운 작업에 단순한 코드를 쓰고 어려운 작업에 필요한 구조를 적용해야 한다. 프론트엔드는 기존 컴포넌트와 토큰을 지키면서 더 좋은 화면을 검토해야 한다. 이 품질 평가·피드백 루프는 라우터 구현 다음 단계이며 현재 라우팅만으로 보장되지 않는다.
